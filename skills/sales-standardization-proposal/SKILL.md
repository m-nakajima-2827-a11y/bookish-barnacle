# 営業標準化 提案書スキル

顧客企業の営業体制を「担当者が違っても、必要な情報が漏れず、一定品質の提案と引き継ぎができる状態」にするための提案書を作るスキルです。

元になったのは、オフショア開発会社（SHIFT ASIA）向けに作成した17枚構成の提案書です。業種・商材・組織規模が変わっても使えるよう、**論理構成・各スライドの型・デザイン・品質基準** を汎用化しています。

## このスキルの考え方（提案の背骨）

提案全体を貫く主張は次の1文です。どの顧客向けでも、ここはぶらさないでください。

> 営業の均一化で最初に取り組むべきは、資料の統一や研修ではなく、受注・失注案件の分析に基づいて「その会社の標準営業プロセス」を定義することである。

理由は次のとおりです。資料や研修は「何を標準とするか」が決まって初めて中身が決まります。また、AIやSFAも、入力項目とプロセスが揃っていなければ品質の均一化につながりません。この順序を顧客に納得してもらうことが、提案の成否を分けます。

進める順番（全顧客共通の5ステップ）:
1. 受注・失注要因を分析する（営業診断）
2. 営業プロセスと各段階の完了条件（次へ進む条件）を統一する
3. ヒアリング・提案・見積・引き継ぎをテンプレート化する
4. KPIと案件レビューの基準を統一する
5. 成功事例を蓄積し、AIとロールプレイで定着させる

## 作業の流れ

### Step 1. 入力情報を整理する

ユーザーから受け取った情報を、次の観点で整理します。全部そろっていなくても進めて構いません。不足している部分は仮説で補い、本当に重要な不足だけを確認します（確認は最大3点程度）。

| 観点 | 例 | 不足時の扱い |
|---|---|---|
| 顧客企業の事業・商材 | 受託開発、SaaS、広告運用、Web制作 | 公式サイト・求人情報から推定し「仮説」と明記 |
| 営業の担当範囲 | 新規開拓、既存深耕、見積作成、デリバリー連携 | 求人情報が有力な根拠になる |
| 引き継ぎ先 | 開発、制作、運用、CS、海外拠点 | 商材から推定 |
| 営業組織の規模・体制 | 人数、新規/既存の分担 | 「次のアクション」の確認事項に回す |
| 既知の課題・要望 | 提案品質のばらつき、引き継ぎトラブル | 4領域の課題仮説で補完（Step 2） |
| 使用ツール | CRM/SFA、議事録ツール | 確認事項に回す |
| 期間・予算・提案者の立場 | 90日、コンサル/社内企画 | 90日計画を既定にする |

**事実と仮説を分けてください。** 顧客が言ったこと・公開情報に書いてあることは事実です。それ以外は「想定」「仮説」と書きます。根拠のない数値（受注率○%改善など）や実績は作りません。効果を数値で示す必要がある場合は「目安」「想定」と明記し、試算の前提も書きます。出典を使ったら、該当スライドの脚注に出典名を入れます。

### Step 2. 課題仮説を4領域で立てる

属人化した営業組織の課題は、ほぼ次の4領域に分けられます。顧客の情報をこの枠に当てはめ、各領域で3〜4個の具体的な症状を書きます。

1. **提案内容が担当者によって異なる**: 提案範囲・提案方法・訴求軸（価格か品質か）がばらつく
2. **ヒアリング内容にばらつきがある**: 目的・予算・納期・決裁者・現状・品質課題の確認漏れ
3. **営業と引き継ぎ先の連携に負荷がかかる**: 要件未整理のまま渡る、前提や対応範囲の認識ずれ、約束内容の齟齬
4. **案件管理が担当者の感覚に依存する**: 見込み度の基準、次回行動、失注理由、事例が残らない

3つ目の「引き継ぎ先」は顧客ごとに読み替えます（開発チーム、制作チーム、海外拠点、運用・CS部門など）。業種別の読み替えは `references/customization-guide.md` を参照してください。

課題・施策・効果は一貫させます。スライド3で挙げた課題には、スライド5〜15のどれかで必ず打ち手が対応している状態にしてください。対応のない課題は削るか、施策を足します。

### Step 3. 構成を決める

標準は17枚構成です。各スライドの目的・要素・可変部分は `references/slide-blueprints.md` に詳しく書いてあるので、執筆前に必ず読んでください。

| No. | スライド | 役割 |
|---|---|---|
| 1 | 表紙 | タイトルと提案の一文要約 |
| 2 | 結論 | 最初にやるべきこと、5ステップ、「均一化」の定義 |
| 3 | 想定される現在の課題 | 4領域の課題仮説（根拠を脚注に記載） |
| 4 | 営業診断 | 分析対象と確認項目 |
| 5 | 標準営業プロセス | 段階 × 必須行動 × 次へ進む条件 |
| 6 | ヒアリングの標準化 | 共通ヒアリングシート（3領域） |
| 7 | ヒアリング後の1ページサマリー | 引き継ぎ先が判断できる形式 |
| 8 | 提案パターンの標準化 | 顧客課題 → 入口提案 → 拡張提案 |
| 9 | 提案書の基本構成 | 12項目の型 |
| 10 | 見積・引き継ぎの標準化 | 必須項目と承認フロー |
| 11 | 案件評価基準 | スコア項目とA〜D区分 |
| 12 | KPI設計 | 新規／既存／組織品質の3階層 |
| 13 | 案件レビューの運用 | 週次（意思決定）と月次（傾向） |
| 14 | 営業ナレッジの体系化 | 残すものと成功事例フォーマット |
| 15 | AI活用 | 段階別の活用案と「AIから始めない」注意 |
| 16 | 90日実行計画 | 現状把握 → 標準化 → 定着・改善 |
| 17 | 次のアクション | 合意事項と事前確認事項 |

規模の調整:
- **短縮版（8〜10枚）**: 1, 2, 3, 4, 5, 6+7を統合, 10, 12, 16, 17。初回訪問・経営層向け。
- **詳細版（20枚前後）**: 現状分析の結果、業種別の提案パターン、ツール導入計画、体制図を追加。
- ユーザーが構成を指定した場合は、その構成に従います。このスキルの構成は、指定がない部分を埋めるために使います。

### Step 4. スライド案を書く（テキスト出力）

まず、テキストで構成案を出します。各スライドに次の5点を書きます（ユーザーがPowerPoint・Googleスライド・Claudeのどれでもそのまま使える形式です）。テンプレートは `assets/outline-template.md` にあります。

- **ページタイトル**: 1文で結論を言い切る「ストーリータイトル」（例:「9段階の営業プロセスごとに『次へ進む条件』を定義し、③⑤⑧を重点管理します」）。全角40字以内、2行以内が目安です。表紙・結論・次のアクションのような構造スライドだけは、ラベル型（「結論：〜」「次のアクション：〜」）にします。
- **要点**: 1〜3行
- **詳細**: 箇条書き（1項目2行以内、です・ます調ではなく体言止めでも可。ただし1枚の中では揃える）
- **図表案**: どの型で見せるか（カード、表、フロー、タイムラインなど）
- **出典・注記**: 仮説・出典・前提

文章は簡潔な「です・ます調」にします。経営者にも現場にも伝わる言葉を使い、抽象論（「営業力を強化します」）ではなく、具体的な行動・担当・期間で書きます。

### Step 5. スライドを生成する

ユーザーが資料ファイルを求めたら、`references/design-system.md` のデザイン仕様と生成手順に従って作ります。

- **Googleスライド**: pptxを生成してGoogleドライブにアップロードし、Googleスライドに変換します。Googleスライドのコネクタがあれば、変換後に書き出した画像で全ページを確認して修正します。
- **PowerPoint**: pptxを生成して渡します。
- いずれの場合も、ファイルを作る前に `pptx` スキルと（Googleスライドの場合は）`google-workspace` スキルを読み込んでください。デザイン・QAの詳細はそちらにあります。

### Step 6. 品質チェック

渡す前に、次を確認します。

- [ ] スライドのタイトルだけを順に読んで、提案の筋が通る
- [ ] スライド3の課題すべてに、後半で打ち手が対応している
- [ ] 事実と仮説が区別され、仮説には「想定」「仮説」「目安」がついている
- [ ] 根拠のない数値・実績・事例がない
- [ ] 出典を使ったスライドに脚注がある
- [ ] 顧客名・業種固有の用語（引き継ぎ先、サービス名）が全スライドで統一されている
- [ ] 前の顧客の固有名詞（例: SHIFT ASIA、ベトナム、SHIFTグループ）が残っていない
- [ ] 画像で確認し、文字のはみ出し・重なり・単語の途中での改行がない
- [ ] 最後に「次のアクション」と、顧客に確認したい事項がある
