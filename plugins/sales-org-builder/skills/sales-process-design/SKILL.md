# 標準営業プロセス設計

営業の段階に名前をつけるだけでは標準化にならない。各段階で「何をすれば次に進んでよいか」を、誰が見ても同じ判断になる言葉で定義することが目的である。これにより、案件の見込み度の判断、レビュー、売上予測、引き継ぎの品質がそろう。

## 入力

- `sales-diagnosis` の結果（現行プロセス図、ボトルネック、優先課題3つ）があれば必ず使う。
- 診断がない場合は、標準の9段階（`references/stage-library.md`）を起点に、顧客の商材・営業スタイルに合わせて仮置きし、「仮説」と明記する。
- 顧客がすでにSFA・CRMのフェーズを持っている場合は、その名称を活かし、完了条件の定義を足す形にする。名称を変えると現場の負担が増えるため。

## 手順

### 1. 段階を決める
`references/stage-library.md` の9段階から始め、顧客に合わせて統合・分割する。目安は6〜9段階。段階が多すぎると入力されなくなり、少なすぎるとボトルネックが見えない。
- インバウンド中心: ①ターゲット選定を「リード評価」に置き換える
- 単発の取引: ⑨継続提案を省く
- 引き継ぎ先がない（営業が納品まで担当）: ⑧を「納品準備」に置き換える

### 2. 段階ごとに4項目を定義する
| 項目 | 書き方 |
|---|---|
| 必須行動 | その段階で必ず行うこと（動詞で書く） |
| 次へ進む条件 | 第三者が確認できる事実で書く。「温度感が高い」ではなく「決裁者と面談済み」「予算額を確認済み」 |
| 成果物 | その段階で残す記録（ヒアリングシート、案件サマリー、提案書、見積依頼書、引き継ぎシート） |
| 関与者 | 営業以外に関わる人（責任者、PM、技術担当、法務など） |

### 3. 重点管理する段階を選ぶ
診断のボトルネックと優先課題から2〜3段階を選ぶ。診断がなければ、③課題ヒアリング、⑤社内設計、⑧引き継ぎを既定にする。重点段階には「責任者の確認」か「チェックリストの充足」を条件に加える。

### 4. 案件スコアを設計する
`references/deal-scoring.md` の8項目×0〜2点を起点に、顧客の受注理由・失注理由に合わせて項目を入れ替える。A〜Dの区分と、区分ごとの対応（誰が支援するか、レビューの頻度）を決める。点数の区切りは、診断データがあれば過去案件に当てはめて検証する。

### 5. ステージ別受注確率を決める
売上予測に使う場合だけ設定する。過去データがあれば、各段階に到達した案件のうち最終的に受注した割合を使う。なければ `references/deal-scoring.md` の目安を「仮置き」として使い、3か月後に実績で見直すと書く。

### 6. 運用ルールを書く
- 段階を進める操作は誰がいつ行うか
- 次へ進む条件を満たさないまま進めた場合の扱い（週次レビューで差し戻す、など）
- CRM・SFAに入力する項目と、入力のタイミング
- 見直しの時期（試験運用後と、その後は四半期ごと）

## 成果物

| 成果物 | 形式 | 中身 |
|---|---|---|
| 標準営業プロセス定義書 | Googleスプレッドシート | 「プロセス定義」シート（段階×必須行動×次へ進む条件×成果物×関与者×重点）、「案件スコア」シート（入力欄と自動計算、A〜D判定）、「受注確率」シート |
| 運用ルール | Googleドキュメント | 目的、段階の一覧、重点段階、スコアの使い方、入力ルール、見直しの時期 |
| プロセス図 | スライド1枚またはドキュメント内の図 | 段階を左から右に並べ、重点段階を強調色にする |

案件スコアのシートは、評価項目ごとに0・1・2のプルダウン（データの入力規則）を設定し、合計点と区分（A〜D）を数式で自動判定できるようにする。

## Googleファイルの作り方

作成前に `google-workspace` スキルを読み込む。新規ファイルはGoogleドライブで作り、中身はGoogleスプレッドシート・Googleドキュメントのコネクタで書き込む。プルダウンや数式はスプレッドシートの書式更新で設定する。変更は同じファイルに加え、リンクを変えない。

## 次のスキル

各段階の「成果物」は `sales-templates` で作る。案件スコアと段階は `sales-kpi-review` の週次レビュー・KPIの入力になる。
